# C3: постоянный образ, класс и уровень компаньона

База: `3e667527e`, ветка `integration/ai-4.8`. Решение о создании:
[ADR-0010](ADR-0010-COMPANION-CHARACTER-SNAPSHOT.md).
Результаты: [C3_VALIDATION_2026-11-06](C3_VALIDATION_2026-11-06.md).

## Путь игрока

1. Создать желаемую внешность обычным редактором персонажа Aion.
2. Войти владельцем и вызвать `//companion sources`.
3. Выбрать образец своего аккаунта, ник и, если образец стартового класса,
   будущую специализацию. Например, `//companion create Vasya` для готового
   клерика; `//companion create Vasya Mira cleric` для жреца; `-` вместо ника
   оставляет имя образца. Текущий персонаж также может быть образцом.
4. `//companion summon` вызывает независимого `[AI:C]Vasya` или `[AI:C]Mira`.
   `//companion status` показывает постоянный класс, уровень и состояние синхронизации.

Для 2–10 букв ника префикс не входит в пользовательский ввод. Занятое имя
отклоняется до создания тела. Класс, имя и снимок закрепляются в первом claim;
повтор с другими аргументами не переопределяет существующего спутника.

## Реализация

- `CompanionSourceDAO`: account-scoped SQL по авторизованному владельцу; исключает
  персонажей, ожидающих удаления, и требует полную appearance row. Ни inventory,
  ни XP/skill/quest state образца не загружаются.
- `CompanionAppearanceSnapshot` и `CompanionBlueprint`: проверяемый снимок всех
  52 целочисленных native полей и роста, без mutable shared references.
- `CompanionCreationClaim`/`CompanionPersistenceDAO`: снимок сохраняется **до**
  создания тела. Коллизии имён блокируются UNIQUE, JSON и display name сверяются
  при чтении. Recovery не обращается к образцу.
- `DefaultCompanionPlayerCreationGateway`: стандартный `newPlayer/storeNewPlayer`,
  level 1, стартовое семейство выбранного класса, собственный штатный стартовый
  набор сервера. Никакого полного клонирования Player и fake connection.
- `CompanionProgression`: проверенный owner/body/host/claim и текущая lease,
  класс/уровень 1:1 по владельцу; обычные autolearn навыки из native skill tree
  по классу, уровню и расе. Stigma, deity/avatar, профессии и специальные unlocks
  этим механизмом не выдаются. Стартовые профессии native создания не копируются
  с образца и не развиваются C3.
- Узкий `PlayerCommonData.synchronizeCompanionProfile` обновляет только профиль
  server-controlled тела, не вызывает обычный `onLevelChange`. Нет reward packs,
  StarterKit, фракционных/квестовых hooks, изменения расового соотношения или
  фиктивного ascension quest. Обычные `setExp/setLevel` людей остаются прежними.
- Нативные `PlayerSkillList`/`SkillLearnService` добавляют/удаляют обычные навыки
  и их пассивные эффекты. При снижении уровня недоступные обычные навыки удаляются.
  Статистики пересчитываются штатно с сохранением доли HP/MP, без полного лечения
  и сброса cooldowns. Классовые cast/Heal и ротации — C4.
- Перед spawn выполняются сверка appearance с blueprint и первая синхронизация.
  В действующей lease изменение уровня проверяется общим scheduler без SQL в
  цикле. При смерти/активном cast синхронизация ожидает допустимого состояния;
  до её завершения не запускаются следующие боевые/квестовые шаги maintenance.
  Новые потоки на персонажа не создаются.
- `BodyCheckpoint` перед live-переходом защищает предыдущий валидный snapshot.
  Если native mutation бросит исключение, scheduler удалит тело, а cleanup сохранит
  прежний снимок вместо частично изменённого. Успех снимает эту защиту; последующий
  dismiss сохраняет новое состояние штатным C2 checkpoint.

## Включение и откат

`ai.companions.profile.enabled=false` по умолчанию. Нужны существующие global,
companions, creation и goal_persistence flags и закрытый service account.
При выключении profile flag новые profile bodies не вызываются; активные
удаляются общим механизмом feature gating. Они не становятся legacy WARRIOR.

Наши preproduction определения `ai_companion_creation_claims` дополнены
`blueprint` и `display_name` в `aion_gs.sql`, `update.sql`,
`ai_companion_creation.sql`. Для проверки используется свежая отдельная БД.
`CREATE TABLE IF NOT EXISTS` не обновит структуру существующей таблицы:
старую экспериментальную установку нельзя считать обновлённой после повторного
запуска этого DDL. Рабочая БД в этом проходе не мигрируется и не сбрасывается.

Старые claims без blueprint сохраняют прежний режим и не получают выбранный
профиль задним числом. Автоматической конверсии/смены класса существующего
компаньона нет; для C3 нужен новый owner на подготовленной схеме либо отдельная
чистая тестовая БД. При откате кода с созданными C3 телами выключить AI, а не
запускать старую class-validation против продвинутых тел.

## Следующие границы

C4 реализует боевое/лечебное занятие с native skill execution. C5 — собственная
экипировка и передача предметов; поэтому соответствие класса/уровня C3 ещё не
означает экипировку полноценного персонажа высокого уровня. C6/C7/C8 сохраняются.
W0, LLM, граждане, автономные легионы и экономика не входят в этот этап.
Клиентская проверка всех стадий остаётся отложенной по решению владельца.
