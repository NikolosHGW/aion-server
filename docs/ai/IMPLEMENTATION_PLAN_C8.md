# C8: повторяемая приёмка компаньона

База: C7 `b4415d3ff`. Начало: 2026-11-06. Scope — C1–C7, без A1/W0/LLM.

## Два уровня приёмки

1. Автоматический серверный прогон: чистая схема → создание двух профилей → реальные
   предметы и rollback транзакции → restart → native навыки/отмена → restart →
   геодата/движение → native quest hook/intent → restart → 0/2/10 тел и cleanup → restart.
2. Совместная клиентская проверка по [матрице](COMPANION_ACCEPTANCE_MATRIX.md).
   Этот gate остаётся открытым до реального игрового прохода; серверный PASS его не заменяет.

## Повторяемый стенд

После сборки reactor с `-Dmaven.test.skip=false` запустить
[`tools/ai/run_companion_acceptance.py`](../../tools/ai/run_companion_acceptance.py):

```powershell
python tools/ai/run_companion_acceptance.py --repo C:/dev/aion/latest/aion-server --output C:/Temp/aion-c8-new-run --java 'C:/Program Files/Eclipse Adoptium/jdk-25.0.1.8-hotspot/bin/java.exe'
```

Требования: Python 3.9+, Java 25, Docker с уже доступным `mariadb:11.4`, geodata
репозитория и свободные localhost-порты 53416/17786. Output должен быть новым
каталогом вне checkout. Скрипт не скачивает Docker image и не собирает код сам.

Стенд создаёт свой MariaDB в tmpfs, импортирует `game-server/sql/aion_gs.sql`,
назначает отдельного пользователя только для `ai_c8_runtime`. Параметр произвольной
БД не предусмотрен; Java entry point проверяет точный тестовый endpoint до старта.
В `finally` проверяются имя, метка и tmpfs принадлежащего прогону контейнера;
он останавливается. Пароль удаляется из оставленного runtime config.
Рабочая БД/клиент/пользовательские настройки не используются. Берутся tracked конфиги
репозитория; сетевые адреса переопределяются в новом runtime.

Каждая из девяти фаз запускается в отдельной JVM. Результат требует exit code 0
и явного `C8_RUNTIME_PASS`, без `C8_RUNTIME_FAIL`. Timeout — 240 секунд на фазу.
`report.json` хранит HEAD, hash рабочего diff, исходников Java/runner и собранного пакета,
результаты, длительности и SHA-256
логов. Логи и runtime остаются в output, БД удаляется. При ошибке прогон останавливается;
исправленный вариант проверяется в новом output на новой базе.

## Что именно проверяет нагрузка

Ноль, два, затем десять реальных server-controlled Player с native appearance,
классом, инвентарём, World/registry, geodata и движением. Чередуются семьи гладиатора
и клерика, уровень 10. Используется обычный scheduler: 1 действие, 2 ms, период 200 ms;
по 120 проходов на сценарий. Отчёт показывает p50/p95/max длительности прохода,
число превышений, время сценария и общий использованный heap JVM без принудительного GC.
Это короткий тест follow/управления, не прогноз пропускной способности населения,
осады, LLM или 10 одновременно кастующих персонажей.

Owner connectivity подставляется как явный test seam в CompanionContext; соединения
не создаются и `Player.isOnline` не меняется. Private session record заполняется
fixture через reflection только в test-коде. Выбор занятия, status, dismiss,
checkpoint и retry после SQL-ошибки вызывают настоящий CompanionService.
Это проверяет его доменную логику, но не обходится за проверку login/summon/пакетов.

Превышение бюджета последним синхронным действием теперь учитывается даже при
достигнутом лимите действий. Добавлены длительность последнего и самого долгого
прохода. Бюджет не прерывает native/SQL-вызов; долгий вызов остаётся риском,
который нужно видеть в измерениях.

## Условия завершения

Серверная часть C8: зелёная сборка, девять фаз PASS, проверенные ссылки/границы,
матрица поддержанного поведения и отдельный коммит. Продуктовая приёмка C8:
дополнительно закрыты клиентские пункты матрицы. До неё функции остаются default-off,
production rollout не разрешается этим отчётом автоматически.
