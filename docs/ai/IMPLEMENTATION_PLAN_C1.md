# C1: свой компаньон у каждого игрока

Статус: спроектировано по коду `60c7a17fe`, реализация ещё не начата.
Дата: 2026-11-04. Порядок определён в [DELIVERY_PLAN.md](DELIVERY_PLAN.md).

## Результат

Два обычных игрока одновременно создают и вызывают собственных компаньонов,
дают им команды follow/stay/assist и выбирают цели независимо друг от друга.
Выход, смерть, повторный вход или устаревший callback одного игрока не меняют
состояние второго и не удаляют новое воплощение прежнего тела.

Это этап жизненного цикла. Навыки, лечение, уровень, новая навигация и автономные
граждане реализуются следующими шагами; C1 сохраняет уже существующие игровые действия.

## Подтверждённые точки изменения

| Файл | Нынешнее ограничение | Изменение |
|---|---|---|
| `CompanionService.java` | Поле `session`, один `lastRemovalReason`, callbacks без идентификатора сессии, глобальная блокировка summon | Поиск по owner ID и companion ID; команды проверяют точный runtime owner; callbacks содержат поколение сессии |
| `ServerControlledPlayerRegistry.java` | `playersByRole` допускает ровно одного участника роли | Уникальность по object ID; отдельная политика ёмкости роли; route spike остаётся одиночным |
| `SyntheticPlayerScheduler.java` | Бюджет есть, фактическая отзывчивость нескольких спутников не доказана | Проверить отсутствие голодания и задержки; не создавать отдельный future на каждого AI |
| `CompanionService.removeRuntimeCompanion/verifyAbsent` | Очистка глобального поля сессии | Удалять индекс только при совпадении конкретной записи; проверить все остальные регистрации |
| `CompanionService.isActiveCompanion/companionDied` | Проверяется единственная сессия | Определять сессию по конкретному телу и attribution, не выбирать первый объект роли |

| `AIConfig.java`, `config/main/ai.properties` | Нет продуктового лимита числа активных компаньонов | Явный ограниченный лимит, понятный отказ при исчерпании; существующие флаги остаются default-off |

создать все классы заново.

## Контракт сессии

- Постоянная связь owner→body остаётся в существующей схеме. C1 не переносит старую БД.
- Одному owner ID соответствует не более одной активной сессии; одному body ID —
  не более одного активного воплощения. Запись содержит точные ссылки на owner/body
  и уникальное поколение, а не только переиспользуемые числовые ID.
- Проверка лимита и резервирование происходят атомарно. Ошибка load/spawn снимает
  только собственную резервацию. Лимит учитывает и незавершённый spawn.
- Нельзя держать общую блокировку сервиса вокруг загрузки БД и дорогих операций мира.
  Резервирование, выполнение и подтверждение разделяются; обновления одной сессии сериализуются.
- Callback смерти, scheduler error или потери владельца действует только на
  то поколение, для которого он был создан. После dismiss/resummon старый callback ничего не удаляет.
- `getActive(COMPANION)` не превращается в «первый попавшийся компаньон».
  Вызывающий код явно указывает owner/body; перечисление применяется только для общего shutdown/диагностики.
- Очистка сохраняет порядок combat attribution относительно world/aggro cleanup.
  Ошибка очистки одного спутника не должна прерывать shutdown остальных.
- Legacy template mode не позволяет одновременно клонировать один DB object ID
  для разных владельцев. Многопользовательский сценарий проверяется с постоянными
  телами, созданными через product creation.

## Предлагаемая реализация по небольшим частям

1. Выделить тестируемую модель владения активными сессиями: reserve/commit/remove
   с проверкой идентичности и поколения, отдельные индексы owner/body и лимит.
   Использовать её в реальном сервисе, не оставлять неиспользуемую абстракцию.
2. Перевести registry на несколько компаньонов, сохранив единственность route spike
   и проверки коллизий с World/PlayerContainer/movement manager.
3. Перевести summon, команды владельца и read-only status на конкретную сессию;
   привязать tick, quest tracking и removal callbacks к ней.
4. Перевести ownerLeaving, death, dismiss и shutdown на ту же модель. Убедиться,
   что observer и attribution каждого владельца снимаются независимо.
5. Дать обычному игроку доступ только к собственным пользовательским командам
   после проверок ownership и изоляции. Административные диагностика/массовые
   операции остаются с административными правами.
6. Добавить лимит и диагностику, провести многопользовательскую приёмку.

На этом этапе не выдаются общие account warehouse, broker или trade полномочия.
Прежде чем включить их в C2/C5, требуется отдельное решение об изоляции
account-scoped состояния. Один shared AI-host текущего прототипа не объявляется
готовой моделью экономики нескольких независимых жителей.

## Автоматические проверки

- Два владельца могут резервировать разные тела, оба получают независимые сессии.
- Второй summon одного owner или того же body отклоняется без утечки регистрации.
- Два одновременно выполняющихся reserve не превышают глобальный лимит.
- Ошибка между reserve и world spawn освобождает только свою запись.
- Устаревший cleanup после повторного summon не удаляет новую сессию с теми же ID.
- Команда/событие чужого владельца, другой runtime object или другой generation не принимается.
- Завершение одной сессии сохраняет registry, movement, goal, observer и attribution второй.
- Shutdown посещает все сессии даже после ошибки одной; повторное завершение безопасно.
- Scheduler обслуживает несколько actor без голодания; остановленный actor не продолжает действие.
- Существующие single-companion, quest и combat сценарии остаются рабочими.
  Проверки исходников обновляются только там, где изменился согласованный контракт;
  вместо проверки имени поля предпочтительны проверки поведения.
- Пакетная сборка и динамическая компиляция команд проходят. Чистая БД принимает
  несколько owner/body связей, уникальные ограничения не позволяют дубликаты.

## Проверка двумя клиентами

1. На отдельной чистой тестовой БД создать двух обычных владельцев и настроить
   закрытый AI-host, creation и действующие флаги. Не использовать общую шаблонную копию.
2. Оба игрока создают и вызывают своих компаньонов. Оба клиента видят оба тела.
3. Развести владельцев, включать follow/stay/assist независимо; каждый статус
   показывает только его спутника, выбранную цель и результат действия.
4. Один выходит и входит; второй продолжает движение и разрешённый бой.
5. Повторить dismiss/summon, позднее появление наблюдателя и смерть спутника.
   Проверить отсутствие дублей и чужих удалений.
6. Достичь настроенного лимита: следующий summon отклоняется понятным сообщением,
   после освобождения места срабатывает, repeat create не создаёт новое тело.
7. Отключить AI и завершить сервер. Все тела, observers и scheduled entries исчезают;
   после старта сохраняется прежний ownership и выбранные цели.

Критерий завершения C1: реализация, автоматические проверки и эта клиентская
приёмка зафиксированы отдельно. Только успешная компиляция не закрывает этап.
