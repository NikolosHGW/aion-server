# План реализации: компаньон → самостоятельный игрок → живой мир

Дата: 2026-11-04. Проверенная база: `integration/ai-4.8`, `60c7a17fe`.
Владелец выбрал порядок: **полноценный компаньон, затем самостоятельные AI-игроки**.
Это текущий порядок работ; исторические планы 2A–2G остаются описанием принятых экспериментов.
`feature/ai-mvp` сохраняется без изменений.

## Дополнение к продуктовой цели от 2026-11-06

Владелец подтвердил расширенное видение **Living World + Autonomous Society**:
компаньон как спутник личной истории; память/отношения; живой мир, меняющийся
без людей; самостоятельные ИИ-персонажи и легионы со своими союзами,
договорённостями, войнами и осадами; свободные планы игрока; отсутствие FOMO.

**Это направление не заменяет очередь C1–C8.** На момент интеграции V2 следующим
был C3; теперь серверные C1–C8 завершены, а полная игровая приёмка открыта. Утверждены
продуктовые направления, а конкретные event schema, persistence, способы
off-screen strategic state и межфракционная политика — **Proposed** до ревью
исходников/ADR и независимых проверок.

Рабочий план узких срезов находится в
[IMPLEMENTATION_PLAN_LW](IMPLEMENTATION_PLAN_LW.md); новые области описаны в
[LIVING_WORLD_ARCHITECTURE](LIVING_WORLD_ARCHITECTURE.md),
[COMPANION_STORY_PARTNER_SPEC](COMPANION_STORY_PARTNER_SPEC.md) и
[AUTONOMOUS_SOCIETY_SPEC](AUTONOMOUS_SOCIETY_SPEC.md).

Сверка с кодом и границы предложения:
[интеграционный отчёт 2026-11-06](LIVING_WORLD_INTEGRATION_REVIEW_2026-11-06.md).
[W0](IMPLEMENTATION_PLAN_W0.md) первоначально был отдельным предложением.
После разрешения владельца 2026-11-07 реализована его узкая серверная часть:
[аудит](W0_IMPLEMENTATION_2026-11-07.md), [валидация](W0_VALIDATION_2026-11-07.md).
P1 и Living World не добавляют обязательную зависимость к исходному C7. ADR-0007…0009
остаются Proposed; Accepted ADR и журналы приёмки не переписываются.

Ключевое разделение: companion/citizen XP, loot, kinah, trade — только native
подтверждённые действия; стратегическое изменение региональных состояний
может происходить без online-наблюдателя в будущем world slice, но не
подменяет native рейды/осады и не начисляет AI фиктивные личные награды.

**Добавляем к плану, не вместо него:** W0 (verified event и память) с отдельным
клиентским/DB тестом → P1 (компаньон знает совместное прошлое и отказ владельца)
→ W1 (маленький динамический регион) → S1/S2 (цели, отношения, AI-группа/легион)
→ S3 (территория и договоры) → S4/S5 (native осады и межфракционные отношения
после server/client audit). W0 можно проектировать одновременно с C3; не
запускать runtime world dependencies впереди нужных gateways.

## Слои и смысл команд

1. **Нативные механики Aion.** Проверяют реальный мир, классы, дистанцию, препятствия,
   mana, cooldowns, предметы, награды и права на действие.
2. **Общий набор действий персонажа.** Принимает намерение, проверяет текущую сессию
   и вызывает штатную механику. Его используют обе роли AI.
3. **Исполнители занятий.** Следование, помощь в бою, лечение, путешествие, квест,
   сбор, покупка. Хранят текущий шаг, умеют завершаться, отменяться и восстанавливаться после отказа.
4. **Решения персонажа.** Компаньон учитывает команды и состояние владельца;
   гражданин выбирает цели по потребностям, склонностям, расписанию и известному миру.
5. **Население и необязательный LLM.** Менеджер населения распределяет сессии и
   нагрузку. World Director может менять приоритеты; LLM — обсуждать цели и предлагать намерения.
   Быстрые решения движения и боя остаются локальными, мир работает при выключенном LLM.

Scheduler обслуживает эти слои; сам по себе он не является «мозгом».

Примеры будущего API ниже — контракт проектирования, не уже существующие Java-методы:

| Намерение | Исполнение | Как узнаём результат |
|---|---|---|
| `MoveTo(destination)` | Навигация строит разрешённый маршрут, movement controller проходит его | Достигнута точка / путь отсутствует / движение прервано |
| `Follow(actor)` | Отдельное занятие использует проверенные шаги движения | Держит дистанцию / потерял владельца / заблокирован |
| `Attack(target)` | Боевое занятие выбирает обычную атаку либо разрешённый изученный навык | Реальные игровые события; отмена, смерть и потеря цели прекращают занятие |
| `UseSkill(skillId, target)` | Штатные проверки и skill engine | Начат cast, затем завершён, отменён или отклонён |
| `Heal(target)` | Политика лекаря выбирает свой доступный лечебный навык и вызывает `UseSkill` | Настоящий результат навыка; прямое изменение HP не используется |
| `UseItem`, `Equip`, `Loot`, `Interact` | Узкие доменные сервисы с проверками принадлежности и доступности | Подтверждённое нативное изменение состояния |
| `Cancel(actionId)` | Остановка только соответствующего действующего действия | Повторная отмена безопасна; старый запрос не отменяет новую сессию |

Для продолжающихся действий нужны ID, поколение сессии, deadline, состояния
`ACCEPTED/RUNNING/SUCCEEDED/REJECTED/CANCELLED/FAILED` и понятная причина отказа.
Принятие команды не означает достижение цели. Повторные запросы не должны повторять
покупку, награду или расход предмета. Движение, cast и смена цели согласуются между собой.

Не строим заранее сотни заглушек «на все случаи»: каждый новый метод появляется
вместе с работающим сценарием, проверками и наблюдаемым результатом. `GoTo("город")`
сначала разрешает известное место и доступный способ путешествия, а не телепортирует тело.

| C6 | Навигация к целям и сопровождение в разных ситуациях | Застревание имеет ограниченное восстановление; смерть, relog и переходы не оставляют потерянные тела |
| C7 | Каталог занятий и удобное управление, расширение за пределы одного квеста | Владелец выбирает доступное занятие; спутник помогает и объясняет следующий шаг по реальным событиям |
| C8 | Сквозная приёмка, нагрузка, отключение и повторный запуск | Повторяемый сценарий от чистой установки до совместной игры и восстановления состояния |

Зависимости: C2 нужен до изменения/сохранения прогрессии; C3 — до обещания
классового боя; C4 и C6 — до автономных боевых занятий; C5 использует C2.
В C2 добавляем только действия, необходимые следующему сценарию, без отдельной
переписи всего AI. В C4 включён короткий checked подход рядом с владельцем;
дальние маршруты и восстановление пути остаются C6.

Для C8 составляется явная матрица поддерживаемых классов, диапазонов уровня,
локаций, способов передвижения, квестовых типов и видов смерти/возврата.
Её наполняют проверенными сценариями. Поддержка двух выбранных ролей и наземного
маршрута не объявляется поддержкой всех классов, полёта, данжей и всего Aion.
Первую игровую версию проверяем на боевой и лечебной роли; расширение до остальных
частей продукта остаётся в плане, а не исчезает из задачи.

## Почему развитие нельзя добавить одним setLevel

В текущей 4.8 `PlayerCommonData.setLevel()` ведёт через `setExp()` в
`PlayerController.onLevelChange()`. Вместе со статистиками и обычными навыками
там вызываются quest/faction hooks, бонусные наборы, StarterKit и изменение
расового соотношения. Слепой вызов может выдать компаньону лишние награды.

В C3 добавлен отдельный проверенный путь продуктовой синхронизации:
[контракт](IMPLEMENTATION_PLAN_C3.md) описывает класс/вознесение/смену уровня,
сохранение и исключённые побочные эффекты.
Stigma и специальные unlocks не выдаются автоматически. У компаньона нет отдельной
доли XP; у самостоятельного гражданина, наоборот, будет собственный штатный XP.

Навыки тоже не сводятся к `applyEffectDirectly`: часть подготовки cast и проверок
времени находится в `CM_CASTSPELL`. Для AI проверенные условия должны быть доступны
доменному сервису. Использование предметов сейчас проверяет `Player.isOnline()`,
который означает наличие соединения: нужен узкий проверяемый путь server-controlled
actor, без fake connection и без общего изменения смысла online для всех игроков.

## После компаньона: самостоятельная жизнь

| Шаг | Работа | Проверяемый результат |
|---|---|---|
| A1 | Роль гражданина, личное состояние и нативные события | Он получает свои quest hooks, XP и loot; правила attribution компаньона на него не распространяются |
| A2 | Один полный самостоятельный цикл | Войти → выбрать доступную цель → дойти → выполнить → получить настоящую награду → использовать результат → выйти → продолжить после restart |
| A3 | Разные профили и расписания, ограниченное население | 0/10/20 AI с измерением CPU, памяти, пауз, очередей и задержек; занятия заметно различаются |
| A4 | Группы, затем легионы | Согласованная цель, роли, вступление/выход, лидерство и обычное распределение наград |
| A5 | Экономика | Добытый предмет → продажа → покупка заработанными средствами → реальное потребление, без дублей |
| A6 | Данжи и сложный контент | Отдельный проверяемый сценарий для каждого типа механики, затем расширение |
| A7 | Разговоры и необязательный LLM/World Director | Высокоуровневые намерения проходят тот же исполнитель; отключение нейросети не останавливает игру |

Перед A1 нужно пересмотреть ранние общие `isServerControlled`-ветки в `PlayerController`:
ограничения прототипа компаньона не должны подавлять собственные квестовые и зональные
события гражданина. Не создаём вторые версии движения, навыков и инвентаря.

У каждого жителя свой выбор следующего занятия. Менеджер населения решает, сколько
сессий сейчас можно запустить и где есть свободная ёмкость. Центральный Director не
управляет каждым ударом и не создаёт фиктивную активность. Без игрока-наблюдателя
AI по-прежнему живёт через настоящие серверные действия, без выдачи offline XP.

## Как ведём работу

- Рабочая ветка — `integration/ai-4.8`; историческую `feature/ai-mvp` не меняем.
- Этот файл определяет текущий порядок; `PROJECT_STATE.md` — фактическое состояние.
  На ближайший этап заводим подробный план, после завершения фиксируем результаты.
  Подробные планы: [C1](IMPLEMENTATION_PLAN_C1.md), [C2](IMPLEMENTATION_PLAN_C2.md).
  После завершения кода и серверных проверок каждого этапа создаём отдельный коммит.
- Один небольшой законченный сценарий на изменение: реализация, значимые тесты,
  чистая тестовая база при необходимости, проверка сервера и сценарий проверки клиентом.
  Работа внутри согласованного этапа выполняется без подтверждения каждой функции.
- Статусы различаются: «спроектировано», «реализовано», «автотесты прошли»,
  «проверено в клиенте». Предыдущую ручную приёмку нельзя автоматически перенести на новый код.
- Ручные проверки объединяем по игровому сценарию. Пока пользователь проверяет клиент,
  можно продолжать независимые аудиты и тесты; непроверенную механику не объявляем принятой.
- Для разработки можно поднимать новую БД из версионируемых SQL-схем. Сохранение старой
  экспериментальной базы не требуется. Проверка сохранения новых персонажей после restart
  остаётся обязательной частью функциональности.
- До первого production-релиза AI, по решению владельца от 2026-11-06, определения
  наших AI-таблиц можно переписывать в существующих SQL-файлах. Не наращиваем цепочку
  миграций и совместимость ради промежуточных экспериментальных схем: при необходимости
  поднимаем чистую тестовую БД. История схемы сохраняется в Git вместе с кодом.
  Актуальные определения в `game-server/sql/aion_gs.sql`, AI-части `update.sql`,
  `ai_companion_persistence.sql` и `ai_companion_creation.sql` должны совпадать.
  Это правило относится к нашим ещё не выпущенным AI-расширениям; изменения upstream 4.8
  сохраняют свой порядок обновления. После первого production-релиза применённые
  миграции фиксируем, дальнейшие изменения схемы оформляем новыми миграциями.
- Обновления 4.8 принимаем небольшими порциями между законченными изменениями и снова
  проверяем точки интеграции. Внешний Living World Engine не выделяем в отдельный процесс
  ради самого разделения; границы переносимых правил и Aion API сохраняем в коде.
- Существенные продуктовые развилки выносим отдельно: классы/роль, опыт потери при смерти,
  модель предметов, взаимодействие с группой. Конкретные технические имена методов,
  структура тестов и обычное исправление ошибок не требуют отдельного согласования.
