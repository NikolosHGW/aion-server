# C2: серверные проверки, 2026-11-06

База — `integration/ai-4.8`, предыдущая точка отката C1 `7a4131204`.
Контракт и ограничения: [IMPLEMENTATION_PLAN_C2.md](IMPLEMENTATION_PLAN_C2.md).

## Автоматические проверки

Полный reactor `mvn -o package -Dmaven.test.skip=false` прошёл:
**287 тестов**, failures/errors/skips **0/0/0** (game-server 281,
login-server 5, commons 1). Пакеты собраны на Java 25.
Последняя уточняющая проверка покрывает ActionSession, TrackedMovementGateway,
BodyCheckpoint и CompanionSessions, включая отказ старому поколению после relog.

Новые проверки подтверждают:

- принятая команда движения ещё не является достигнутой точкой;
- повтор запроса не выполняется заново, даже после вытеснения receipt;
- чужой UUID, другой payload и истёкший deadline отвергаются;
- старая отмена не останавливает новое действие, synchronous close не теряется;
- смена точки follow не порождает лишних остановок;
- неудачный checkpoint сохраняет исходный снимок для повторной записи;
- template и неактивированный summon не записывают тело;
- отказ одного владельца не затрагивает другого;
- отменённая сессия сохраняет резерв тела до завершения cleanup.

## Чистая MariaDB и перезапуск

Отдельный локальный контейнер MariaDB 11.4, отдельная свежая схема `aion_gs.sql`,
новые служебные тестовые персонажи. Запущен настоящий game-server с данными 4.8.
Два процесса JVM последовательно выполнили фазы `create` и `restore` проверкой
`CompanionC2RuntimeProbe` из репозитория. Она не создаёт клиентских соединений.

Подтверждены создание двух разных тел и стабильные binding/claim; неизменность
имени БД при runtime alias; сохранение изменённого навыка, однократного расхода
реального экземпляра предмета, HP/MP и обоих типов cooldowns; повторная запись
одного snapshot без повторного расхода; сохранение после полного завершения и
нового запуска JVM.

Намеренная SQL-ошибка в конце транзакции не оставила записанного изменения
навыков или расхода предмета. Чужой owner был отклонён. Второе тело осталось
неизменным. Отдельная контрольная запись общего склада служебного аккаунта
не загружается в AI body и не перезаписывается checkpoint.

Обычный login server в этой доменной проверке не запускался: ожидаемая запись
«Could not connect to login server» относится к отдельному неиспользуемому
тестовому порту, а не к ошибке persistence. Нативная загрузка данных и
компиляция handlers завершились.

Для повторения probe нужна отдельная пустая схема из `game-server/sql/aion_gs.sql`,
URL `jdbc:mysql://127.0.0.1:53410/ai_c2_runtime?...` в `config/mygs.properties`,
нативные `data/config`, собранные test-classes/classes и зависимости game-server.
До фазы `create` добавить в эту временную схему контрольный предмет общего склада:

```sql
INSERT INTO inventory
  (item_unique_id,item_id,item_count,item_owner,item_location,item_skin)
VALUES (990001,182400001,17,880002,2,182400001);
```

Запускать `com.aionemu.gameserver.services.ai.CompanionC2RuntimeProbe create`,
затем `restore` в новом JVM, сохранив рабочий каталог и файл
`c2-expectations.properties`. Между фазами должно пройти меньше 10 минут:
проверяется действующий cooldown, после этого срока его штатно отбрасывает загрузчик.
Порты game/login connection должны быть отдельными от рабочих серверов.

## Что ещё не принято в игре

По запросу владельца клиентские проверки C1/C2 отложены до общего прохода:
два обычных владельца, видимость имён/экипировки, follow/stay, dismiss/resummon,
смерть, relog, отключение AI и штатный shutdown. Серверный probe не подтверждает
анимацию, видимость или UX команд. Новый путь сохранения эффектов и восстановления
после смерти требует отдельной игровой проверки.

Checkpoint выполняется при штатном удалении тела. Проверка не доказывает
сохранность после аварии JVM/ОС или принудительного выключения при недоступной БД.
Транзакционные передачи предметов и операции экономики ещё не добавлены (C5/A5).
