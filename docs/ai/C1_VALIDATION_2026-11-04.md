# C1: отдельный компаньон у каждого владельца

Дата: 2026-11-04. Ветка: `integration/ai-4.8`.
Статус: реализация и автоматическая проверка готовы; по решению владельца
клиентская приёмка отложена на следующий совместный запуск.
Историческая `feature/ai-mvp` не менялась.

## Что изменено

- `CompanionSessions` резервирует owner ID и body ID, включая незавершённую
  загрузку. У каждой записи свой токен поколения и блокировка; операции с БД
  и миром не выполняются под общим монитором сервиса.
- Команды, tick, quest maintenance, смерть и удаление привязаны к конкретной
  записи. Для команды и logout проверяется точный объект владельца, для смерти —
  точный объект тела. Поздний callback старой записи не может удалить новую.
- Registry допускает несколько `COMPANION`; `ROUTE_SPIKE` остаётся одиночным.
  Вызов `getActive(COMPANION)` запрещён, произвольный первый спутник не выбирается.
- Общий scheduler пропускает занятую сессию. Ошибка cleanup одного actor не
  прекращает последующие проходы общего scheduler. Новые потоки/futures на
  каждого компаньона не создаются.
- Shutdown сначала закрывает приём новых summon и отменяет все резервации,
  затем пытается удалить каждую запись, включая незавершённые. При неполной
  очистке запись сохраняется для повторного удаления; ёмкость освобождается
  после проверки внешних регистраций. Attribution сохраняется до очистки мира.
- `//companion` имеет уровень доступа 0. Команда не принимает чужой player ID
  или цель для управления. `//aiplayer` остаётся административной командой уровня 9.
  Legacy template доступен только staff и по-прежнему не клонирует один DB ID.
- `ai.companions.max_active = 10` — начальный ограниченный лимит, включая
  незавершённые summon. Это не обещание измеренной производительности под нагрузкой.
  Все существующие feature flags по умолчанию выключены.
- При параллельном создании на настоящей БД обнаружен deadlock: блокировка
  отсутствующих owner bindings мешала независимым вставкам. Финализация теперь
  использует READ COMMITTED и блокировку существующего claim владельца.
  Известный откатившийся deadlock повторяется максимум три попытки; ошибки
  соединения, уникальности и неудавшийся rollback автоматически не повторяются.

## Выполненные проверки

Полная Maven package-сборка на Java 25: **271 тест**, failures/errors/skips —
**0/0/0** (265 game-server, 5 login-server, 1 commons).
Включена динамическая компиляция обеих AI-команд и проверка доступа обычного
персонажа к `companion`, с сохранением уровня 9 у `aiplayer`.

Новые проверки покрывают отдельные команды двух владельцев, подмену runtime
identity, дубли owner/body, 40 конкурентных запросов при лимите 3, отмену загрузки,
устаревшее поколение, shutdown с ошибкой одного участника, пропуск занятого actor,
отсутствие tick после отмены, обслуживание десяти actor при бюджете одного действия,
непрерывность scheduler после ошибок и ограниченный повтор SQL deadlock.

Отдельный запуск собранного сервера на **MariaDB 11.4**, со свежими
`aion_gs.sql` и `aion_ls.sql`, подтвердил:

1. Два обычных владельца создаются штатным путём; одновременное создание их
   компаньонов возвращает разные постоянные тела.
2. Повторный create возвращает прежнее тело, начальные навыки и инвентарь
   загружаются штатно, без клиентского соединения у компаньона.
3. Снятие registry/attack observer/attribution первого сохраняет второй.
4. БД отклоняет дубли owner/body/name; неудачные вставки не меняют второе владение.
5. После завершения и нового запуска game-server оба create возвращают
   `ALREADY_EXISTS`, прежние связи и разные тела сохраняются.

Это доменная интеграционная проверка. Она **не** выполняла реальный summon/follow
через клиент, показ моделей, движение двух владельцев, смерть в бою и relog.
Не вводились fake connection или обход проверок владельца ради теста.

## Клиентская приёмка перед закрытием C1

На отдельной тестовой установке нужны два обычных аккаунта, закрытый AI-host,
geodata mode ON и can-see checks, creation и companion flags. Использовать
свежую SQL-схему; перенос старой БД не нужен. В обоих клиентах:

```text
//companion create
//companion summon
//companion status
//companion stay
//companion follow
```

При включённых принятых combat/goal flags дополнительно проверить `assist on`,
`assist off`, `today`, `goal choose` и `goal status`. Развести владельцев,
удалить спутника только у одного, повторить summon, выйти/войти одним клиентом,
проверить смерть, появление наблюдателя, лимит, отключение AI и остановку сервера.
Полная матрица — в [IMPLEMENTATION_PLAN_C1.md](IMPLEMENTATION_PLAN_C1.md).

Решением владельца от 2026-11-06 клиентская приёмка объединена с последующими
этапами; разрешено продолжить C2 до неё. C1 остаётся без игровой приёмки.
Следующий шаг разработки — C2: общий контракт действий и
сохранение изменяемого тела. Уровни, классовые навыки, лечение, свободная
торговля и самостоятельная жизнь в C1 не добавлены.
