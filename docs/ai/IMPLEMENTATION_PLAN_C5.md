# C5: собственные предметы компаньона

Дата: 2026-11-06. Этап после [C4](IMPLEMENTATION_PLAN_C4.md).
Код и проверки относятся к ограниченному первому варианту; игровая приёмка отдельная.

## Доступный сценарий

`//companion items list` показывает реальные ID экземпляров, количество и слоты.
`items equip ObjectId SlotMask` / `items unequip ObjectId` вызывают штатный Equipment:
класс, уровень, мастерство, пол, раса, ранг, вместимость, статистики и видимое оружие.
Stigma и ещё не привязанные bind-on-equip вещи пока отклоняются: для их подтверждения
нужен отдельно спроектированный интерфейс владельца. Подтверждение клиента спутнику
не подделывается.

`items use ObjectId` использует штатный SkillMethod.ITEM для мгновенного HP/MP зелья
на самого спутника. Только один SkillUseAction, без cast delay, subeffects и произвольных
скриптов. Native расход экземпляра, cooldown и ограничения сохраняются. Общая проверка
состояния вынесена из PlayerRestrictions; человеческий `canUseItem` по-прежнему требует
online. Вход компаньона авторизует текущий owner lease. Второй quest journal не создаётся.

## Передача без дублирования

`items give ObjectId` / `items take ObjectId` ставят одну заявку на целый предмет/стек.
Команда возвращает UUID квитанции и явно сообщает: передача произойдёт при выходе
владельца к выбору персонажа. До выхода её отменяет `items cancel`. Это осознанная
граница C5: штатный live ExchangeService сохраняет два инвентаря раздельно и не даёт
нужной транзакционной гарантии. Обмен без выхода требует будущего общего native
inventory gateway с согласованными блокировками всех участвующих live writers.

После native logout, checkpoint спутника и сохранения владельца, пока leave-world
guard ещё запрещает повторный вход, CompanionItemTransferDAO:

1. Проверяет отсутствие обоих тел в мире и отсутствие незавершённого cleanup.
2. Блокирует строки персонажей, сверяет неизменяемую связь claim/binding/host account.
3. Проверяет прежнюю квитанцию по владельцу и UUID: повтор не исполняется снова.
4. Сверяет оба инвентаря и все сохранённые поля переносимого экземпляра.
5. В одной транзакции меняет `inventory.item_owner` и записывает квитанцию.

ID, количество и связанные с тем же ID камни сохраняются. Не создаются предметы,
копии или кинары. Не поддерживаются частичные стеки, kinah, special cube, временные,
упакованные, привязанные и неторгуемые вещи. Получатель должен иметь свободный слот;
автоматического объединения стеков нет. Изменившийся предмет отклоняет заявку.

Старая detached Java-ссылка после попытки commit помечается недопустимой для записи:
запоздалый native InventoryDAO autosave не вернёт вещь прежнему владельцу. Его записи
и handover согласованы через read/write fence: обычные native сохранения остаются
параллельными, короткая передача получает write lock. C2 checkpoint отдельно проверяет
владение каждым экземпляром. При неоднозначной ошибке commit следует смотреть
`items receipt UUID`; отсутствие подтверждения не называется успехом.

Заявка до выхода существует только в сессии. Crash до выполнения отменяет её;
запуск сервера не воспроизводит неподтверждённые пожелания. Завершённая передача и
квитанция хранятся в БД. Это не система фонового offline заработка.

## Включение, сохранение, откат

`ai.companions.items.enabled=false` по умолчанию. Нужны также AI/companions и
продуктовый профиль. Отключение запрещает новые действия и отменяет ещё не выполненные
передачи при выходе; уже подтверждённая native ownership остаётся действительной.
Отключать сохранение тела нельзя: C2 сохраняет расход/экипировку/cooldowns.

Таблица квитанций включена в `aion_gs.sql`, `update.sql` и `ai_companion_items.sql`.
Рабочая БД и клиент не меняются автоматически. Перед включением на существующей
тестовой установке нужен этот SQL. Наши prerelease схемы можно пересоздавать.
